# 走过功能实施路线图

## 固定命名与执行规则

- 中文功能名、页面名和内容 Tag 统一为“走过”。
- 程序内部类型、路由、目录、资源和数据契约统一使用 `zouguo`。
- 页面路径固定为 `/zouguo/`，独立内容目录固定为 `content/zouguo/`。
- Markdown 是正式内容唯一来源；JSON 只由 Hugo 自动生成，不手工维护。
- 图片保存在 R2，Markdown 只记录公开 URL。
- D1 只保存草稿，不作为正式内容源。
- `/zouguo/` 聚合独立走过、唠叨和随笔，不复制原内容。
- 严格执行“一步一验收、一阶段一提交”；上一步未通过不进入下一步。
- 第 10 步是人工闸门，前 9 步完成后也不能自动执行。

## 第 1 步：确定数据契约

先把未来所有模块共同遵守的数据格式固定下来。

执行内容：

- 定义独立走过 Markdown Front Matter。
- 定义统一的走过 JSON Schema，并带契约版本号。
- 明确三种来源：`zouguo`、`laodao`、`post`。
- 明确 `occurredAt` 和 `publishedAt` 的含义。
- 明确地点、行政区域、图片、正文和原内容链接字段。
- 明确 GeoJSON 经纬度顺序始终为 `[longitude, latitude]`。
- 定义“走过”为保留 Tag。
- 增加合法与非法数据样例。

验收标准：

- 三种来源都能转换成同一种 JSON Item。
- 经纬度不会出现顺序混乱。
- 唠叨和随笔带“走过”Tag 却没有结构化地点时，校验必须报错。
- Schema 有版本号，未来可以升级。
- 这一步只确定规则，不改变现有页面。

## 第 2 步：建立独立走过内容管线

执行内容：

- 使用 `content/zouguo/` 保存独立走过 Markdown。
- 创建走过 Markdown 模板。
- Hugo 自动扫描独立走过。
- 自动生成 `/zouguo/index.json`。
- 走过页面改为读取构建生成的数据。
- 当前手写的 `zouguo_prototype.json` 退出正式数据链路。
- 原型数据暂时转成开发测试内容，保持当前页面效果。

验收标准：

- 新增一个 Markdown 后，地图和列表自动出现。
- 修改 Markdown 后，地图内容自动变化。
- 删除 Markdown 后，走过记录自动消失。
- 全程不修改生成 JSON。
- 当前 PC 界面和交互没有视觉回退。
- Hugo 严格构建和项目检查通过。

## 第 3 步：接入唠叨和随笔

执行内容：

- 扫描带“走过”Tag 的唠叨。
- 扫描带“走过”Tag 的随笔。
- 唠叨提取文字、图片、地点和日期。
- 随笔提取标题、链接、封面和正文图片。
- 随笔不复制长文正文。
- 增加来源类型和原内容链接。
- 正确处理 Tag 删除和原内容删除。

验收标准：

- 唠叨添加“走过”Tag 后自动进入地图。
- 删除 Tag 后自动退出地图。
- 随笔在走过页只显示标题和图片。
- 点击随笔标题能进入原文章。
- 缺少地点的 Tag 内容不能悄悄进入错误位置。
- 同一篇内容不会因为多次构建产生重复数据。

## 第 4 步：地点标准化与行政区域自动化

这是保证以后新增地点不需要手工维护地图的关键步骤。

执行内容：

- 定义稳定的 `placeId`。
- 保存国家、省/州、市、地点名称和代码。
- 处理同一个地点不同写法的归并。
- 建立坐标到行政区域的解析流程。
- 构建时自动提取“去过地区”的边界。
- 替换目前手工维护的测试边界数据。
- 增加地点精度和隐私级别。

验收标准：

- 新增一个从未去过的省份，省份自动高亮。
- 新增一个海外国家，国家自动高亮。
- 不需要手工编辑 `zouguo_boundaries.json`。
- 多次去同一个地方能归并成同一个地图地点。
- 相近但不同的地方不会被错误合并。
- 私人或敏感地点可以选择模糊坐标。

## 第 5 步：发布 Worker 和统一草稿

当前 App 使用的线上发布接口和仓库中的 Publisher Worker 并不完全一致，这一步先把真实服务代码纳入统一管理。

执行内容：

- 整理当前 App 实际使用的发布 Worker。
- 增加独立走过的发布、详情、更新和删除接口。
- 保留现有唠叨发布兼容性。
- 草稿表增加 `kind` 和 `payload_json`。
- 迁移现有唠叨云草稿。
- 为发布接口增加字段校验、路径校验和幂等处理。
- 补齐接口契约测试。

验收标准：

- 旧版唠叨仍然可以发布、修改和删除。
- 独立走过可以发布为单独 Markdown。
- 同一请求重复提交不会生成两条内容。
- 唠叨草稿迁移后不丢失。
- 走过草稿能完整保存文字、地点、日期和图片顺序。
- 未授权请求不能调用发布接口。
- Worker 测试全部通过。

## 第 6 步：重构 App 发布入口

执行内容：

- 右上角保留一个统一发布按钮。
- 点击后弹出原生菜单：“唠叨一下”“记录走过”。
- `PublishView` 改成模式化编辑器。
- 图片、预览、排序、上传和草稿共用一套代码。
- 不复制两套发布页面。
- 草稿列表增加内容类型标识。

验收标准：

- 可以分别进入唠叨和走过模式。
- 两种模式共用图片处理和草稿能力。
- 原有唠叨发布功能没有回退。
- 唠叨草稿仍然可以继续编辑。
- App 不出现两个容易混淆的发布按钮。

## 第 7 步：实现“现在这里”

执行内容：

- 获取当前定位。
- 使用 MapKit 反向解析地点。
- 显示定位精度和地图预览。
- 允许修改展示名称，但保留真实坐标。
- 默认发生时间为当前时间。
- 支持纯文字、单图和多图。
- 支持本地自动草稿和云草稿。
- 正式发布后触发博客构建。

验收标准：

- 允许定位时，可以获得有效地点和坐标。
- 拒绝定位时有明确提示，并可以改用事后补记。
- 修改地点显示名称不会把经纬度清空。
- 草稿退出 App 后可以恢复。
- 图片顺序发布前后保持一致。
- 发布后记录能出现在博客地图上。
- 地图行政区域同步高亮。

## 第 8 步：实现“事后补记”

执行内容：

- 增加“现在这里 / 事后补记”模式切换。
- 使用 `MKLocalSearch` 搜索地点。
- 展示多个候选结果。
- 选择结果后显示地图预览。
- 允许修正地点名称和地图位置。
- 单独选择实际经过日期。
- 优先匹配已有地点。

验收标准：

- 输入“青山湖”等关键词能看到多个候选。
- 系统不会未经确认直接选择第一条结果。
- 选中后能保存正确经纬度。
- 可以补录过去的日期。
- 发布日期和实际经过日期不会混淆。
- 再次选择已有地点时能正确归并。

## 第 9 步：完成唠叨和随笔发布联动

执行内容：

- 唠叨发布页增加“同步到走过”开关。
- 打开开关后自动加入“走过”Tag。
- 没有地点时禁止作为走过发布。
- 随笔编辑器选择“走过”Tag 后，自动出现地点编辑区。
- 走过记录始终回到原来源编辑。
- 删除原内容或取消 Tag 后自动退出走过页。

验收标准：

- 普通唠叨不受影响。
- 打开开关的唠叨会出现在走过页。
- 随笔走过只显示标题、图片和文章链接。
- 在原唠叨中修改图片后，走过页自动更新。
- 在原随笔中修改标题后，走过页自动更新。
- 删除原内容后，不残留孤立记录。

## 第 10 步：迁移、全量测试和上线

执行内容：

- 确认视觉原型测试数据保持已清理，不重新混入正式内容。
- 添加少量真实走过记录验证。
- 检查浅色、深色地图。
- 检查年份筛选、地点聚合和多图灯箱。
- 检查 App 草稿、发布、编辑和删除。
- 检查 Worker 安全和错误恢复。
- 检查走过 JSON 体积及页面性能。
- 检查手机端页面。
- 建立正式上线前回滚点。

验收标准：

- 独立走过、唠叨、随笔三种真实来源都能工作。
- App 到 GitHub、Hugo、JSON、地图全链路打通。
- 无需手工修改生产 JSON 和边界数据。
- 所有严格构建、JavaScript、Swift、Worker 测试通过。
- 浏览器控制台无错误。
- 页面没有持续高 GPU 占用。
- 旧唠叨和随笔功能没有回归。
- 上线异常时可以退回当前 PC 原型状态。

人工闸门：第 10 步不会因前 9 步完成而自动开始，必须等待 Koobai 明确口令。
